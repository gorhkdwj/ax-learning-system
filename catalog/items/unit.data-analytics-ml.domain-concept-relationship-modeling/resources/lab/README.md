# 질문 기반 도메인 개념·관계 모델링

기본 학습 인터페이스는 [오프라인 HTML 교재](../course/index.html)입니다. 이 문서는
JavaScript를 사용하지 않거나 인쇄하여 학습할 때 사용할 수 있는 동등한 정적 실습서입니다.

이 자료는 특정 회사나 비공개 강의 사례를 복제하지 않는 공개·합성 D2 실습입니다.
목표는 온톨로지 도구 설치가 아니라 실제 질문에서 필요한 개념·관계·상태를
도출하고, 가장 단순한 충분 표현을 선택한 뒤 서로 다른 도메인으로 전이하는
것입니다.

## 시간과 완료 계약

- 이 Unit의 기본 학습량은 **10시간(600분)**입니다.
- 기존 RAG Set이 소유한 **2시간 검색 표현 선택 Probe**를 연결하면 권장 D2
  경로는 총 12시간입니다.
- 같은 모델링 오류가 두 전이과제에서 반복될 때만 1~120분의 보충학습을 수행하고
  재평가합니다. 시간을 채우기 위한 보충학습은 하지 않습니다.
- 사전진단을 통과한 학습자는 이미 설명할 수 있는 읽기와 안내 절차를 줄일 수
  있지만, 두 독립 전이과제와 사람 의미 검토는 건너뛰지 않습니다.

공개 예제와 개인 학습 산출물을 분리하십시오. 실제 답안과 회고는 Vault 또는
사용자가 선택한 비공개 위치에 보관하고 공개 저장소에는 넣지 않습니다.

## 1. 개념·비교 학습 — 120분

### 1.1 사전진단 — 20분

자료를 보기 전에 다음 질문에 답하십시오.

1. taxonomy·schema·ontology·knowledge graph가 각각 해결하는 문제는 무엇입니까?
2. 클래스와 인스턴스, 속성과 관계, 값과 상태를 어떤 기준으로 구별합니까?
3. JSON·RDBMS·그래프 중 어떤 조건에서 더 복잡한 표현을 승인합니까?
4. 일반 RAG와 구조화 관계 검색이 각각 실패하기 쉬운 질문은 무엇입니까?

답을 근거와 함께 설명할 수 있으면 해당 개념의 반복 설명은 줄이되, 이후 산출물에서
동일 기준을 실제로 적용해야 합니다.

### 1.2 핵심 구조 — 70분

| 구조 | 주된 역할 | 이 Unit에서의 한계 |
|---|---|---|
| taxonomy | 용어를 상·하위 범주로 탐색·분류 | 속성, 개별 대상, 상태 변화와 복잡한 업무 규칙을 단독으로 충분히 표현하지 못합니다. |
| schema | 데이터의 필드·형식·제약을 정의 | 공유 의미나 도메인 가정을 자동으로 제공하지 않습니다. |
| ontology | 도메인 개념·속성·관계와 필요한 제약을 명시 | 목적과 핵심 질문 없이 넓히면 유지비만 증가하며 정답 모델이 하나로 고정되지 않습니다. |
| knowledge graph | 개별 대상과 관계를 그래프 형태로 저장·연결 | 온톨로지와 동일하지 않으며 단순 조회에 항상 가장 적합한 저장 방식도 아닙니다. |

모델링은 도메인 명사 목록이 아니라 핵심 질문에서 시작합니다. 질문마다 필요한
대상, 값, 관계, 시간에 따라 변하는 상태, 원천과 버전을 표시하십시오. 독립적인
식별과 수명주기가 있는 대상만 클래스 후보로 두고, 상태·수치·열거값은 먼저
속성으로 검토하십시오.

Stanford 가이드는 다음 부분만 선별하여 읽습니다.

- 온톨로지의 목적과 경계
- competency question으로 범위를 제한하는 방법
- 클래스·프로퍼티·제약·인스턴스를 반복적으로 설계하는 절차
- 하나의 정답 모델이 없으며 실제 질문과 유지보수 조건으로 대안을 평가한다는 원칙

RDF·OWL·SPARQL 공식 문서는 전체를 정독하지 않습니다. RDF는 그래프 데이터 모델,
OWL은 온톨로지 표현 언어, SPARQL은 RDF 질의 언어라는 차이와 현재 범위 밖을
설명할 수 있을 정도로만 확인합니다.

### 1.3 개념 비교 산출물 — 30분

`concept-comparison.md`에 다음을 기록합니다.

- 네 구조의 목적·장점·한계와 혼동하기 쉬운 경계
- 같은 질문을 JSON·RDBMS·그래프로 표현할 때의 비용 차이
- RDF·OWL·SPARQL 구현을 현재 범위에서 제외하는 이유
- “온톨로지 또는 그래프가 항상 우수하다”는 주장을 받아들이지 않는 근거

## 2. 클래스·프로퍼티 모델링 — 180분

### 2.1 설계 원리 — 45분

다음 경계를 사례와 함께 설명하십시오.

- 클래스와 인스턴스
- 값·상태와 독립 대상
- 속성과 대상 간 관계
- TBox 수준의 설계와 ABox 수준의 실제 개체
- 프로퍼티의 domain·range와 단일·다중 값 제약
- 현재 상태, 효력 시점, 원천, 버전의 분리

3~7개 클래스는 작은 과제의 범위를 통제하기 위한 실습 제약이지 모든 도메인에
적용되는 보편 법칙이 아닙니다. 질문을 만족하지 못한다면 클래스 수를 억지로
맞추지 말고 범위나 질문을 다시 조정하십시오.

### 2.2 안내 모델링 — 75분

합성 지식문서 라이브러리에 다음 질문이 들어왔다고 가정하십시오.

- 현재 유효한 특정 라벨의 문서는 무엇입니까?
- 이 문서 버전의 원천은 무엇입니까?
- 특정 버전이 속한 문서의 제목은 무엇입니까?

다음 절차로 모델을 작성하십시오.

1. 질문별 명사, 값, 관계와 시간 조건을 표시합니다.
2. 클래스·인스턴스·값·상태 후보를 나누고 경계 사례의 선택 이유를 적습니다.
3. 상태의 기준 시점과 원천·버전을 명시합니다.
4. 각 질문에 `answer_path_ids`를 붙여 필드·관계가 답을 만드는 경로를 추적합니다.
5. JSON·RDBMS·그래프의 충분 여부와 유지비를 비교하고 가장 단순한 방식을 선택합니다.
6. `fixtures/valid.json`은 파일 형식 참고에만 사용하고 분류 근거는 직접 작성합니다.

### 2.3 실패 분석과 수정 — 60분

다음 실패 fixture를 먼저 예측한 뒤 평가 결과와 비교하십시오.

- `too-many-classes.json`: 범위를 벗어나고 값·상태를 클래스로 승격합니다.
- `missing-state.json`: 시간에 따라 변하는 상태를 모델링하지 않습니다.
- `unanswerable-question.json`: 질문의 답변 경로가 없습니다.
- `unsupported-graph.json`: 더 단순한 충분 표현이 있는데 그래프를 선택합니다.

각 오류에 대해 검출 규칙, 실제 의미 오류, 자동검사가 놓칠 수 있는 반례를
구분하여 기록하십시오.

## 3. RAG와 온톨로지의 연결 — 120분

### 3.1 일반 RAG 경계 — 45분

RAG 원 논문의 문제 설정과 검색된 외부 지식을 생성 모델 입력에 연결하는 기본
구조를 확인합니다. 다음을 구분하십시오.

- 검색 실패와 생성 실패
- 유사 문서 회수와 정확한 사실·관계 조회
- 최신성·삭제·권한 조건과 단순 유사도의 차이
- 근거 ID 보존과 답변 보류

### 3.2 구조화 관계 검색 가설 — 45분

자연어 질문을 바로 그래프 기술로 구현하지 말고 다음 후보를 비교합니다.

1. 텍스트·벡터 검색
2. 메타데이터 필터와 관계형 조회
3. 구조화된 관계 질의

온톨로지는 용어와 관계의 의미를 명시하는 모델이며 RAG의 필수 구성요소가
아닙니다. 구조화 관계 질의는 다른 방식이 충족하지 못하는 필수 관계 질문이 있고,
최신성·ACL·추적성 Gate와 추가 유지비를 함께 통과할 때만 승인 후보입니다.

### 3.3 아키텍처·효과 검토 — 30분

`rag-ontology-boundary.md`에 다음을 기록합니다.

- 질문 이해 → 검색 또는 질의 → 근거 → 답변 흐름
- 각 단계의 실패와 관측 가능한 증거
- 온톨로지·관계 모델이 도움이 되는 질문과 도움이 되지 않는 질문
- 효과 주장, 확인된 사실, 아직 검증하지 않은 가설

RDF·OWL·SPARQL 구현, 추론 엔진과 그래프 DB 운영은 수행하지 않습니다.

## 4. 독립 D2 전이평가 — 120분

`transfer-prompts.json`의 두 과제를 각각 60분 안에 수행합니다. 공개 정상 예제의
클래스명을 복사하지 말고 각 도메인의 질문에서 다시 시작하십시오.

1. `templates/model-submission.template.json`을 비공개 학습 위치로 복사합니다.
2. 서로 다른 `submission_id`와 `transfer_task_id`를 부여합니다.
3. 질문·클래스·필드·관계·표현 결정을 작성합니다.
4. 최소 두 가지 초기 오류와 수정 이유를 `corrected_errors`에 기록합니다.
5. 각 모델에 구조 평가기를 실행합니다.

```powershell
python tools/evaluate_domain_model.py <첫-전이-model.json>
python tools/evaluate_domain_model.py <둘째-전이-model.json>
```

자동평가는 구조 누락을 찾는 보조 수단입니다. ID가 존재한다는 사실만으로 질문의
의미에 맞는 답변 경로라는 점을 증명하지 못합니다.

## 5. 사람 의미 검토와 재평가 — 60분

`templates/semantic-review.template.json`을 복사하여 두 모델을 함께 검토합니다.
다음 여섯 기준을 모두 구체적인 근거와 함께 통과해야 합니다.

- 질문과 답변 경로의 실제 의미 정합성
- 클래스·인스턴스·값·상태 분류의 타당성
- 시점·원천·버전 추적성
- 가장 단순한 충분 표현 선택
- 서로 다른 두 도메인의 독립 전이
- 사용자의 구두 설명

완료 검사는 두 모델 파일과 같은 의미 검토 파일을 하나의 Gate에서 함께 검사합니다.

```powershell
python tools/evaluate_domain_learning.py <첫-전이-model.json> <둘째-전이-model.json> <semantic-review.json>
```

같은 오류가 두 과제에서 반복되면 `repeated_error_codes`에 기록하고 최대 120분만
보충한 뒤 재평가합니다. 반복 오류가 없으면 보충학습을 배정하지 않습니다.

## 6. 연결 Probe — 120분

10시간 Unit을 마친 뒤 검색 표현 선택이 현재 D2 경로에 포함되면 다음 Set 소유
Resource를 수행합니다.

- Set: `set.workflow.retrieval-grounded-generation@1.0.0`
- 단계: `choose-retrieval-representation`
- Resource: `resource.workflow.retrieval-grounded-generation.representation-probe@1.0.0`

Probe는 기존 RAG Set에서 계속 `required: false`이므로 이를 건너뛰어도 Set의 기존
필수 경로는 바뀌지 않습니다. 다만 Probe가 배정된 개인 경로에서는 질문 유형별
선택표와 기술 도입 결정 기록까지 제출해야 총 12시간 경로가 완료됩니다.

## 합격 기준

- 개념 비교와 RAG 경계 산출물을 자신의 말로 설명합니다.
- 두 독립 전이 모델이 각각 작은 범위의 핵심 질문을 실제 필드·관계로 답합니다.
- 값·상태를 불필요한 클래스로 승격하지 않습니다.
- 시간에 따라 변하는 정보와 원천·버전을 명시합니다.
- JSON·RDBMS·그래프 선택을 질문 충족과 유지비로 설명합니다.
- 구조 자동검사와 사람 의미 검토를 모두 통과합니다.
- 반복 오류가 있을 때만 제한된 보충학습과 재평가를 수행합니다.
- AI가 초안을 만들 수는 있지만 최종 분류·표현 선택·검증 근거는 사용자가
  자신의 말로 설명합니다.

## 범위 밖

FOL, ASP, OWL 추론, Protégé, Fuseki, SPARQL 구현과 그래프 DB 운영은 이 Unit의
범위가 아닙니다. 필요성이 실제 질문 실패로 입증되면 별도 Unit이나 승인된
Probe로 분리하십시오.
