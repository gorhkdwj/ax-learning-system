# AX 학습 거버넌스

## 1. 목적

이 문서는 AI Agent와 바이브 코딩을 포함한 전사적 AI Transformation 학습공간의
범위, 품질, 평가, 유지관리 원칙을 정의합니다.

현재 사용자의 업무는 우선순위와 실습 맥락을 정하는 중요한 근거이지만,
전체 역량지도와 재사용 학습 라이브러리를 특정 업무에 한정하지 않습니다.

## 2. 적용 구조

학습 시스템은 다음 네 층으로 구성합니다.

1. **전사 AX 역량지도**: 조직 전체에 필요한 역량의 범위와 관계를 보존합니다.
2. **Learning Unit**: 기술, 개념, 패턴, 공학 실천, 제품, SaaS 등을 재사용 가능한
   학습 단위로 관리합니다.
3. **Learning Set**: 업무, 파이프라인 또는 산출물을 위해 여러 Unit과 Resource를
   참조·조합합니다.
4. **개인 우선순위 경로**: 현재 업무가치, 역량 격차, 위험, 선행효과,
   시간과 비용에 따라 동적으로 구성합니다.

전사 지도의 완전성과 현재 학습의 집중도를 동일한 문제로 취급하지 않습니다.
낮은 우선순위 역량도 카탈로그에는 남길 수 있지만 상세 자료 제작은 보류할 수 있습니다.

AI 리터러시, AI 결과 검증, 보안, 개인정보, 저작권·라이선스와 책임 있는 사용은
직무와 관계없이 필요한 공통 역량으로 관리합니다.

## 3. 분류와 범위

### 3.1 분류 원칙

- 대분류와 중분류는 전사 AX 역량의 탐색과 누락 방지를 위해 구성합니다.
- 프론트엔드, 백엔드, UI, UX, DB, AI 등의 예시는 고정 분류가 아닙니다.
- RAG, CSS, PyTorch, Hugging Face, Zapier, Codex Plugin 등의 예시도
  하나의 트리나 동일한 유형을 전제하지 않습니다.
- 각 항목은 `item_type`과 유형 있는 관계를 이용하여 의미를 명시합니다.
- 사용자 화면은 트리, 태그, 그래프 등 여러 보기를 제공할 수 있지만
  정규 메타데이터는 하나만 유지합니다.
- 분류 ID, 정의, 포함·제외, 부모·관련 관계와 상태의 단일 정본은
  `taxonomy/taxonomy.json`입니다. Candidate와 Unit은 Registry의 활성 node를
  참조하며 임의 문자열로 대분류·중분류를 늘리지 않습니다.
- `research_lens`는 누락 방지를 위한 조사 역할이지 조사 시점의 정규 대분류가
  아닙니다. 조사·Coverage·정규화 Gate를 통과한 안정 ID는 canonical domain으로
  전환할 수 있으며 Candidate의 discovery와 provenance에 최초 조사 이력을 보존합니다.
- 프론트엔드·백엔드·데이터 엔지니어링 같은 직무는 여러 역량 node를 조합하는
  역할 보기로 우선 표현합니다. 조사 결과 독립된 안정 범위가 입증되면 중분류나
  대분류로 승격할 수 있습니다.
- 외부 역량·지식체계는 누락과 경계를 교차검증하는 참고체계입니다. 외부 항목과의
  동등성이나 내부 정규 분류를 자동으로 확정하지 않습니다.
- 새 대분류, 기존 ID의 개명·병합·폐기는 영향범위와 이관 계획을 제시하고
  사용자 승인을 받은 뒤 Registry 버전을 올립니다.

### 3.2 범위 발산 방지

후보 항목은 다음 중 하나 이상을 충족해야 카탈로그에 등록합니다.

- 실제 또는 예상되는 전사 업무·산출물·의사결정과 연결됩니다.
- 다른 고가치 Unit 또는 Set의 선수역량입니다.
- 필수 보안·법적·운영 통제입니다.
- 시간 제한형 탐색으로 검증할 전략적 옵션가치가 있습니다.

어느 조건도 충족하지 못하면 과목으로 확장하지 않고 감시목록 또는 제외 기록에 남깁니다.
선정, 보류, 제외, 폐기 결정에는 사유를 기록합니다.

### 3.3 신흥 개념 연구 인입

하네스 엔지니어링, 루프 엔지니어링, LLM Wiki처럼 빠르게 등장하는 명칭은
발견 즉시 Unit으로 만들지 않습니다. 먼저 Trend Signal로 다음을 확인합니다.

- 정규 명칭, 별칭, 잠정 정의와 포함·제외 범위
- 기존 Unit·Signal과의 중복, 부분집합 또는 재명명 여부
- 정의·효과·한계·위험 claim과 각 claim을 지지하거나 반박하는 evidence
- 용어 성숙도, 정의 신뢰도와 효과 신뢰도
- 업무 연결성, 비즈니스 임팩트 가설과 비교 Probe 가능성
- Resource·Adapter·Unit·Probe Set·Set·관찰·기각 중 적합한 목적지
- 소유자, 재검토일, 변화 감지 조건과 과장 방지 문구

Trend Signal은 네 학습 계층 앞의 연구 인입 레코드이며 이수 대상이나 다섯 번째
학습 계층이 아닙니다. 세부 상태 전이와 승격 기준은
`docs/research/trend-signal-governance.md`를 따릅니다.

### 3.4 Phase 2 조사 Candidate

전사 AX 역량지도 Breadth 조사에서 발견한 항목은 정규 Unit이나 Trend Signal로
바로 만들지 않고 Candidate staging 레코드로 먼저 기록합니다.

- Candidate는 후보 정의, 범위, 전이성, 목표 깊이, 실무가치 가설과 근거를 보존합니다.
- Candidate ID는 최초 발견 렌즈를 보존하고 정규 소유 분야는
  `taxonomy.major_domain`으로 분리합니다. `discovery`에는 실제 발견 경로를
  기록하여 교차 분야에서 발견된 항목도 추적 가능하게 합니다.
- `discovery.lens_id`, `taxonomy.major_domain`, `taxonomy.subdomains`는
  `taxonomy/taxonomy.json`의 활성 node와 계층 관계에 맞아야 합니다.
- 후보 간 선행·연관 관계는 최상위 `relations`에서 대상 ID와 정확한 버전을
  참조하며 자유형 확장 필드에 중복 기록하지 않습니다.
- 정규 ID 제안은 실제 Unit·Set ID의 확보나 승격을 뜻하지 않습니다.
- 출처·taxonomy·실무성 감사를 분리하여 같은 에이전트가 발견부터 승인까지
  담당하지 않게 합니다.
- 안정된 후보는 역량지도·Resource·Adapter·Unit·Set으로 라우팅하고,
  신흥·중의적 후보는 Trend Signal로 보냅니다.
- 보류·제외·병합 결정과 재검토 조건도 삭제하지 않고 남깁니다.

세부 실행·샘플링 QA와 완료조건은
`docs/research/phase2-capability-survey-runbook.md`를 따릅니다.

## 4. 필수·선택·우선순위

다음 세 축을 분리합니다.

- **과정상 중요도**: 공통 필수, 역할 필수, 선택, 참고, 필수 통제
- **실행 우선순위**: 지금, 다음, 이후, 관찰
- **선행관계**: 다른 Unit 또는 Set의 실행 전에 반드시 필요한지 여부

선택과목도 즉시 업무효과가 높으면 필수과목보다 먼저 학습할 수 있습니다.
단, 안전 통제와 실제 선행관계는 우선순위 조정으로 건너뛰지 않습니다.

## 5. 실무 적정 깊이

### 5.1 숙련도

| 수준 | 완료 기준 |
|---|---|
| D0 인지 | 용도, 한계와 주요 위험을 설명합니다. |
| D1 안내 수행 | 안내와 예제를 따라 결과물을 만듭니다. |
| D2 독립 수행 | 새로운 소규모 과제를 구현하고 자동검증합니다. |
| D3 운영 수행 | 권한, 보안, 비용, 관측성, 장애와 롤백을 관리합니다. |
| D4 전문 최적화 | 내부 구현이나 프레임워크를 연구·개발하고 최적화합니다. |

보조 도구는 D2, 핵심 파이프라인·에이전트·배포·보안은 D3를 기본 목표로 합니다.
D4는 실제 업무 필요와 기대효과가 입증된 경우에만 포함합니다.
전사 지도에 포함되었다는 이유만으로 모든 사용자에게 같은 D 수준을 요구하지 않습니다.
D0 또는 D1 이수를 독립 실무 수행 능력으로 표시하지 않습니다.

### 5.2 유지보수와 확장

실무 완료 기준에는 필요한 범위에서 다음을 포함합니다.

- 설정과 비밀정보 관리
- 오류 처리, 로그와 상태 추적
- 의존성 및 버전 갱신
- 장애 진단과 복구
- 작은 기능 변경과 확장 지점
- 비용, 성능과 품질 관측

이 항목들이 기술 범위를 크게 넘거나 난이도를 급격히 높이면 현재 Unit의 운영 심화,
별도 Unit, Set 통합 실습, 보류·기각 중 하나로 처리합니다.
전체 학습량이나 목표 수준을 크게 바꾸는 결정은 사용자와 함께 내립니다.

## 6. 학습 설계

### 6.1 범용 Unit 흐름

범용 Unit은 특정 직무 하나가 아니라 전이 가능한 역량을 목표로 합니다.

`역량 목표 → 선수진단 → 핵심 원리·정신모형 → 최소 동작 예제 → 안내 실습
→ 실패·디버깅 → 독립 실습 → 다른 맥락의 전이과제 → 자동검증 → 숙련 판정`

특정 업무는 대표 예시로 사용할 수 있지만 핵심 Unit에는 다른 맥락의 변형 과제를 둡니다.

### 6.2 업무 Learning Set 흐름

업무 중심 흐름은 Learning Set에만 적용합니다.

`업무 현황·병목 → 기대성과·지표 → 자동화 적합성 → 입력·출력·승인·실패 경로
→ Unit 조합 → 연결 실습 → 종단 간 검증 → 운영·복구 → 적용·회고`

Set은 Unit의 공통 설명이나 코드를 복제하지 않습니다.
업무 맥락, 연결 실습, 통합 산출물과 수용 기준만 보유합니다.

### 6.3 실습과 설명

- 지나치게 원론적인 설명보다 실행과 피드백이 있는 실습을 우선합니다.
- 단순 복사 실습으로 끝내지 않고 실패 진단, 독립 변경과 전이과제를 포함합니다.
- 긴 설명이 이해에 필요하면 교재 또는 접을 수 있는 상세 텍스트로 제공합니다.
- 새로운 학습자가 충분한 안내를 받을 수 있게 하되 숙련자는 진단 후 건너뛸 수 있습니다.

## 7. 자료 형식과 이식성

- HTML은 우선 고려 형식이며 특히 HUB, 시각화, 즉시 피드백에 사용합니다.
- 기술 특성상 CLI, 코드, 노트북, 데이터 파일, Markdown, PDF 등이 적합하면 자유롭게 사용합니다.
- 실제 서버, DB, API, Git, 클라우드 또는 에이전트 실행을 불필요한 모의 UI로 대체하지 않습니다.
- 상호작용 자료는 키보드 접근, 명확한 구조와 오류 설명을 제공합니다.
- 핵심 정보에는 동등한 텍스트 및 필요한 정적·인쇄 대체본을 제공합니다.
- 코드 주석은 의도, 계약, 제약, 실패 조건, 설계 이유와 검증 방법에 집중합니다.
- 모든 작업경로는 작업공간 기준 상대경로를 사용합니다.
- 의존성 버전, 잠금 파일, 환경변수 예시, 실행·검증 명령과 기대 결과를 제공합니다.
- 원문·개인 기록·임베딩과 비공개 생성물은 공개 학습 시스템과 물리적으로
  분리하며 `docs/architecture/public-private-storage.md`의 경계를 따릅니다.
- 공개 HTML에 문서 전문, 전체 청크 배열이나 임베딩을 삽입하지 않습니다.

## 8. 평가와 검증

### 8.1 평가 정렬

학습목표, 실습, 산출물, 검증 증거와 합격 기준을 연결합니다.
평가 정렬은 기술 변화를 막는 고정 규칙이 아니라 현재 버전에서 무엇을 검증했는지
표현하는 버전 있는 학습성과 계약으로 사용합니다.

- 안정된 핵심 성과와 변동이 잦은 제품 사용법을 분리합니다.
- 새로운 기술은 `experimental` 또는 `probe` 상태로 등록할 수 있습니다.
- 기술 변경 시 전체 이력을 삭제하지 않고 차이 학습과 통합 평가를 수행합니다.
- 과거 완료 이력은 보존하고 필요한 경우 `갱신 필요`로 표시합니다.
- D2 이상은 기존 예제 재현만으로 완료하지 않고 입력이나 맥락이 다른 과제를 포함합니다.
- D3 평가는 정상 경로뿐 아니라 권한 오류, 외부 의존성 장애, 비용 초과,
  데이터 품질, 보안 사고와 롤백 시나리오를 포함합니다.

### 8.2 검증 증거

상황에 따라 다음 증거를 조합합니다.

- 요구사항과 완료조건
- 입력·출력 및 상태변경 계약
- 단위·통합·E2E·보안·접근성 검사 결과
- AI 평가셋, 도구 호출, 중단 조건과 반복 실행 결과
- 실행 로그, 추적, 실제 외부 상태 확인
- 변경 diff 및 보안·권한 경계의 표적 검토
- 출처, 확인일, 기술과 의존성 버전
- 알려진 한계, 잔여위험, 중단·복구 절차

자동 검사를 통과했다는 사실과 업무적으로 올바르다는 판단을 구분합니다.
고위험·비가역 작업은 인간 승인과 실행 후 상태 확인을 필수로 합니다.
D3 운영 실습은 샌드박스나 시뮬레이션을 기본으로 하며 실제 운영계 변경은 별도 승인 없이 수행하지 않습니다.

## 9. 정확성과 생명주기

- 출처 우선순위는 표준·공식 사양, 공식 문서·릴리스 노트,
  원 논문·공식 소스코드, 검증된 보조자료 순으로 둡니다.
- 사실마다 가능한 범위에서 출처, 적용 버전과 확인일을 기록합니다.
- 사실, 추론, 권고와 불확실성을 구분합니다.
- 코드와 실습은 지정 환경에서 실행 검증합니다.
- AI가 생성한 평가만으로 정확성을 확정하지 않습니다.
- 변경 감시, 정기 검토, 정오표, 대체·폐기 상태를 관리합니다.
- 검증하지 못했거나 오래된 자료는 그 상태를 명시합니다.

## 10. 비즈니스 임팩트

전사 지도에 포함할 가치와 현재 학습을 배정할 가치를 분리합니다.
학습 배정 전 다음 가치를 평가합니다.

- 매출, 비용, 처리시간과 처리량
- 품질, 정확도, 고객 및 직원 경험
- 오류·보안·법적·운영 위험 감소
- 후속 고가치 Set을 가능하게 하는 선행효과
- 여러 업무에서의 전이성과 재사용성
- 제한된 실험으로 미래 의사결정을 개선하는 전략적 옵션가치
- 학습·도입·운영·유지보수 비용
- 기대효과를 뒷받침하는 근거 신뢰도

직접·간접 효과가 없고 필수 통제도 아니라면 카탈로그 참고 항목으로는 남길 수 있으나
상세 교재 제작과 현재 학습 배정은 보류합니다.
불확실하지만 옵션가치가 있으면 전체 과정보다 시간 제한형 Probe를 먼저 수행합니다.

업무 적용 이후에는 완료율이나 생성량보다 실제 성공률, 인간 검토시간, 재작업,
오류, 비용, 품질과 사용 빈도를 확인합니다.

## 11. 메타데이터

모든 Unit, Learning Set, Resource, Trend Signal, Phase 2 조사 Candidate와
Taxonomy Registry는 각각의 JSON Schema에 맞는 메타데이터를 가집니다.
메타데이터가 없는 파일을 규칙 기반 추측으로 분류하지 않습니다.
MVP에서는 모든 참조를 정규 ID와 정확한 콘텐츠 버전으로 기록합니다.

메타데이터에는 최소한 다음 범주를 포함합니다.

- 안정적인 ID, 유형, 버전, 상태
- 제공 역량, 학습성과, 숙련도와 선행관계
- 예상 시간, 환경, 의존성과 비용
- 보안·개인정보·권한·외부 변경 위험
- 산출물, 검증 명령, 루브릭과 합격 기준
- 공식 출처, 확인일, 마지막 실행 검증일
- 소유자, 갱신주기, 대체·폐기 정보
- 접근성 및 대체자료

HUB는 이 메타데이터를 읽어 생성하며 생성 결과를 직접 편집하지 않습니다.
